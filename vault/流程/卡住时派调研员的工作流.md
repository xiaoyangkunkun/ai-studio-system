# 卡住时派调研员的工作流

> 2026-08-16 实战总结（MiMo TTS 500 排障经验）

## 反面教材：今天我犯的错

1. MiMo TTS 返回 500 → 我连续试了 5 种不同格式 → 全部 500
2. 我的思路是"换参数试试"→ 本质是**瞎猜**
3. 浪费了 10+ 分钟和大量 token
4. 老大一句话"你让知远调研一下"→ 知远 2 分钟找到正解：**缺 audio 参数**

## 正确流程（已验证）

```
遇到报错/卡住
    ↓
自己试 1-2 次（合理尝试）
    ↓ 还是不行？
派知远调研（给出：报错信息 + 已尝试的方法 + 需要搞清楚的问题）
    ↓
知远返回正解
    ↓
用正解执行
```

## 什么时候该派知远

| 信号 | 说明 |
|------|------|
| 同一错误试了 2 次以上 | 继续试大概率是浪费 |
| 错误信息含"Param Incorrect"/"Not Found"/"500" | 需要查文档，不是猜出来的 |
| 不确定正确的 API 格式/端点/参数 | 这正是调研员的活 |
| 涉及第三方服务的未知行为 | 官方文档/社区才有答案 |

## 什么时候不该派知远

| 信号 | 说明 |
|------|------|
| 自己能快速验证的（如 curl 一个 URL） | 直接试 |
| 纯配置问题（改 config.yaml） | 自己搞定 |
| 知远已经调研过了 | 看报告，别重复派 |

## 派活模板

给知远的调研请求要包含：
1. **报错信息**（完整错误码 + 消息）
2. **已尝试的方法**（避免重复调研）
3. **需要搞清楚的问题**（具体、可回答）
4. **相关 URL/文档**（省得知远从零找）

## 本次收获

- MiMo TTS 的 `audio` 参数是必须的（文档有写但我没看到）
- `api-key` Header 比 `Authorization: Bearer` 更可靠
- 知远调研 + 军师执行 = 正确分工
- **"自己试"和"查文档"之间的切换点很重要**——试 1-2 次不行就该查
