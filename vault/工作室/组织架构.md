## 新任务自动分流规则(老大无需指定)

- 调研/检索/资料收集/挖矿/方案设计/系统评估 → **知远**
- 写作/文案/润色/公众号 → **墨白**
- 代码/脚本/开发/调试/代码审查 → **技术员·Claude**(需 Windows 在线;代码相关但涉及服务器环境/隐私 → 狗头军师)
- 长文/翻译/知识问答/初稿(2026-08-15 外聘)→ **临时顾问·Kimi**(免费;需 Windows 开机+Chrome 开,不可用走主模型;不建档案不写复盘)
- 长文/翻译/知识问答/初稿/深度推理(2026-08-15 外聘)→ **临时顾问·DeepSeek**(免费;需 Windows 开机+Chrome 开+DeepSeek 登录态,不可用走主模型;不建档案不写复盘;重逻辑推理类优先 DeepSeek,长文写作类优先 Kimi)
- 海外内容/英文母语理解/深度推理(2026-08-15 外聘)→ **海外顾问·Gemini**(免费;**服务器本地 systemd 服务,不依赖 Windows**;依赖服务器 Clash 代理出网;不可用走主模型;不建档案不写复盘;海外内容/深度推理类优先 Gemini)
- 需对话记忆/隐私/审核/微信推送 → **狗头军师**
- 定时任务 → 按上表归属,新增定时任务先问老大确认
- 模糊/新类型 → 狗头军师先做或问老大
- 老大可随时指定「这个给XX做」;小任务/员工忙时狗头军师自己做(成本判断)

## 派活机制 v1(2026-08-15 老大定,防材料压缩不全 + 可用性分层)

### 一、可用性矩阵(派单前必查)
| 顾问 | 可用条件 | 深夜可派 |
|---|---|---|
| 知远/墨白 | 服务器 profile,随时 | ✅ |
| Gemini(海外顾问) | 服务器 systemd 服务 + Clash 活着 | ✅ 24h |
| Kimi(临时顾问) | Windows 开机 + Chrome 开 + WebBridge 连 | ❌ |
| DeepSeek(临时顾问) | 同上 + DeepSeek 登录态 | ❌ |
| 技术员·Claude | Windows 开机 + SSH | ❌ |

规则:深夜定时任务只派服务器侧(知远/墨白/Gemini);Kimi/DeepSeek 派单前先探测(ask_*.py 自带),不可用自动走主模型。

### 二、材料传递规则(治"压缩不全")
- 材料在 vault → **给路径让顾问自己读原文**,军师零转述(顾问均可读 vault)
- 材料在别处 → **原文文件直传**,不经过军师总结
- 只有军师脑内独有的上下文 → **不派,自己做**(符合 token 铁律)
- 禁止:把长材料"压缩总结"后塞进 prompt 再派(复盘测试教训:压缩版输出明显简陋)

### 三、任务类型匹配表
| 任务 | 首选 | 次选 |
|---|---|---|
| 方案设计/系统评估/深度调研 | 知远 | — |
| 长文/公众号/润色 | 墨白 | Kimi |
| 英文/海外内容 | Gemini | — |
| 复杂推理/计算 | DeepSeek | Gemini-thinking |
| 代码/脚本/审查 | 技术员·Claude | — |
| 复盘/日报/总结/问答 | **狗头军师自己做** | — |

### 四、派单前 4 问(军师每次派活必答)
1. 这活我有上下文吗?→ 有就自己做,不派
2. 顾问现在可用吗?→ 探测;不可用换人/走主模型
3. 材料在哪?→ vault 给路径,别处直传原文
4. 输出怎么回?→ 长文落盘 vault + 回传 3-5 行摘要;短文直接回

## 员工扩编机制(2026-08-13 确立)

- 狗头军师持续观察任务分布,发现**单一性高**(高频/重复/可标准化)的工作 → 向老大推荐新招员工
- 触发条件(满足 2 条):某类任务每周 ≥3 次且流程固定 / 每周占用 >2 小时 / 职责边界清晰不重叠 / 成本可接受
- 流程:狗头军师提「扩编建议书」(岗位+职责+技能包+成本)→ 老大批准 → 建员工 → 试运行 2 周 → 评估
- 架构预留岗位:数据员 · 运营员 · 客户专员

## 规则迭代原则(2026-08-14 老大定,元规则)

> **所有规则都不是一成不变的。**

- 管理模式、入职流程、任务分流、员工守则(CLAUDE.md/SOUL)、本架构文档——都是**当前版本**,随实际使用持续迭代
- 触发迭代:老大反馈 / 复盘发现问题 / 真实任务验收暴露短板 / 新员工入职 / 团队或工具变化
- **规则可改是默认,不是例外**:任何人(含员工)发现规则不合理、过时、有更优解 → 提出,评估后更新,并记入迭代日志
- 文档版本演进:v0.x 逐步升级,每次修改注明日期和原因,不追求"一步到位"

### 新旧规则处理细则(2026-08-14 老大定,配套)

- **正文只写当前生效规则**:一眼看懂"现在怎么干",旧规则不进正文,避免混淆
- **被迭代掉的规则 → 移入该文档「迭代日志」小节**:记录 版本/日期/改了什么/废弃原因
- **废弃原因必须记**:这是防止未来改回去重复踩坑的关键(有源可溯,又不受旧规则干扰)
- 所有规则类文档统一带「迭代日志」:组织架构、流程总览、员工守则、技能说明等
- 示例格式:
  ```
  ## 迭代日志
  - v0.1 (08-13) 初始版
  - v0.2 (08-14) 修改 xx;废弃 xx,原因:xxx
  ```
