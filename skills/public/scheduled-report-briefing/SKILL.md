# 定时报告/简报生成(晨报/周报/复盘类 cron 任务设计)

> 来源:2026-08-13 晨报改造实战(用户纠错三次:版本号编造、格式拥挤、输出截断)。

## 触发条件

- 设计或修改定时推送的报告类任务(每日晨报、周报、复盘、监控摘要)
- 报告里含"最新模型/版本/价格/新闻"等**会过时的事实**
- 输出推送到微信等 IM 平台

## 铁律 1:事实类信息必须用"基准文件",禁止从搜索猜测(用户纠错!)

事故:晨报把 Kimi 写成 K2.6(实际 K3)、智谱写成 GLM-5.1(实际 5.2)—— 搜索引擎返回旧文章,agent 没核实就写。

正确做法:
1. 建基准文件(如 `model_baseline.json`):经核实的"截至某日最新版本",存 `~/.hermes/data/`
2. 报告生成时**先读基准**,版本号以基准为准
3. 只查"有没有新发布"(合并检索,最多 2 次,禁止逐家搜索):
   - 检索到**确凿新发布**(官方/权威来源,明确名称)→ 更新基准 + 报告
   - 没有 → 沿用基准
   - 查不到 → 写"**待核实**",**严禁编造版本号**
4. 不确定宁可留白,不犯错(用户原话:"宁可待核实")

## 铁律 2:微信输出格式(用户要求)

- **条目式**:每个条目独立一行,严禁多项挤一行(如 6 家模型塞一行)
- **不用 checkbox**:微信无法打勾,计划/待办用普通列表 `- 事项`
- 分组小标题 + 每条一行,一眼扫完
- **行数硬约束(2026-08-15 限流教训)**:报告类推送 ≤20 行;日常回复也避免超长消息(带表格的长汇报实测触发 iLink 限流,用户等 1 分钟才收到)。长内容落文档(知识库 md + PDF),微信只发摘要。口诀:微信短、文档全。
- 每家/每项一行:如
  ```
  🇨🇳 国内:
  - Kimi:K3
  - 智谱:GLM-5.2
  ```

## 铁律 3:输出必须完整,禁止截断(实战教训)

事故:逐家搜索 10 次,任务跑了 30 分钟,输出在"智谱:GLM-5.2(GL"处截断。

对策:
- **限制检索次数**(合并为 2-3 次),控制任务时长
- prompt 里写死:"总长 ≤N 行,必须完整输出,宁可少搜不可截断"
- 验证:手动试跑后检查输出文件末尾是否自然结束(不是断句)

## 铁律 4:频率匹配信息变化频率(2026-08-13 二次改造)

用户指出:"模型更新频率不是每天,每天搜两次是浪费"。低频信息塞进每日报告 = 每天空转 + 容易编造。

原则:
- **信息变化频率决定报告频率**:每日变化的信息(用量/待办/天气)留每日报告;低频变化的信息(模型版本/Hermes 版本/新闻)降到周报/事件驱动
- 周报里低频信息也要"有更新才写":检索 1 次,有确凿发布 → 写;没有 → 写"本周无重大发布",不硬凑
- 降频落点示例:模型动态 + Hermes 更新检查从晨报移到周复盘(周日),晨报每天省 2 次检索

## 铁律 5:cron 交付格式(干净输出,2026-08-13)

用户要求推送只保留正文,去掉系统包装:

- 配置 `cron.wrap_response: false`(config.yaml,`hermes config set cron.wrap_response false`)→ 去掉 "Cronjob Response: 任务名" 开头和 "To stop or manage this job" 结尾。源码 scheduler.py 注释明确支持,全局生效(所有 cron 推送)。
- 输出格式:标题行 → **空一行** → 正文。在所有 AI 任务 prompt 末尾追加统一格式要求:"标题行与正文之间空一行(如:标题\n\n正文),结尾不附加任何系统提示"。
- no_agent 脚本提醒(echo 固定文案):同样遵守标题/正文空行。
- 称呼统一(如"老大"):排查所有 cron prompt 和提醒脚本,禁用旧称呼。

## 铁律 6:注入上下文会被轻量模型"抄作业"(2026-08-13 复盘翻车事故)

事故:晚间复盘 cron 配了 `context_from`(注入晨报输出),deepseek-v4-flash 面对 359KB 注入内容 + 多步骤指令,直接把**晨报复述一遍当最终输出**交差——Notion/vault 全没写,`last_status` 还显示 ok,表面成功实际空转。

对策:
- **慎用 context_from 注入大段输出**:复盘/汇总类任务只需要自己的数据脚本(对话提取),不需要注入其他报告的输出。复盘修复 = 移除 context_from,只留 daily_chat_extract.py。
- 必须注入时,prompt 加铁律:"上下文里的 X 只是参考数据,**严禁复述**,输出只能是 Y"。
- 轻量模型(deepseek-v4-flash 等)长上下文质量下降明显,注入内容宁少勿多。
- **验证**:跑完后抽查输出文件,确认 Response 是任务产出而不是复述注入内容;写库类任务核对 Notion/vault 是否真有记录(靠 `last_status: ok` 不可信)。
- 会话内补漏:复盘翻车后手动补写时,数据要从 state.db 按时间提取全部会话(不只"我记得的"),避免只凭当前会话视角漏白天内容。

## 数据提取窗口:避免时间盲区(2026-08-13,08-14 扩展)

复盘在 22:00 跑 → 22:00-24:00 的对话当天抓不到(还没发生)、第二天也不覆盖(窗口只查当天) → **无人认领的盲区**。

解法(已落地):
- 提取窗口改为 **"昨天 23:00 → 今天 23:00"**,复盘时间同步改 23:00;昨天尾巴归入今天复盘,单列"昨夜补记"小节。
- 原则:提取窗口必须**无缝覆盖**所有可能对话时间;复盘时刻(脚本运行点)前后的边界要想清楚,不能默认"当天 0 点起"。

### ⚠️ 多任务共用提取脚本:窗口必须参数化(2026-08-14)

复盘和用户习惯整理**共用 daily_chat_extract.py**,但脚本窗口写死"昨 23:00 起"(为复盘 23:00 跑设计的)。习惯整理是 20:00 跑 → 每天 20:00-23:00 的对话**既不在当天(没到点)也不在次日(窗口从昨 23:00 起)→ 永久盲区**。

修复:脚本加 `--window-start <hour>` 参数,各任务传自己运行时间对应的起点:
- 复盘(23:00 跑)→ `--window-start 23`(昨 23:00 起,默认)
- 习惯整理(20:00 跑)→ `--window-start 20`(昨 20:00 起,无缝覆盖上次运行至今)

**检查清单**:凡多个 cron 共用同一数据提取脚本,逐任务核对"脚本默认窗口 vs 任务实际运行时间"是否匹配,否则必有盲区。

### ⚠️ 兜底铁律:提取失败必须从会话库补,禁止靠记忆(2026-08-14)

复盘翻车事故的深层教训:翻车后手动补写时只凭"新会话记忆"导致白天细节缺失(后来从 state.db 补提取 943 条消息才补全)。会话重置(session_reset daily 凌晨4点)只开新会话,**旧会话在 state.db 永久保留**,按时间戳跨会话查询天然可及。

对策:依赖对话提取的 cron(复盘/习惯整理)prompt 里写死【兜底铁律】:
1. 注入的对话记录为空/报错/明显不完整(用户聊了很多但提取很少)→ 用 session_search 或直查 `~/.hermes/state.db`(messages 表按时间戳)补提取
2. **绝不只凭记忆**;补提取后正常执行后续步骤
3. 凌晨 4 点会话重置不影响提取(按时间戳查全部会话,不依赖当前会话)

## 长会话管理:自动重置(2026-08-13)

长会话上下文膨胀 → 报告类任务质量下降(轻量模型尤甚,压缩也丢细节)。配置 `session_reset`(config.yaml):

```yaml
session_reset:
  mode: daily      # daily/idle/both/none
  at_hour: 4       # 每天凌晨 4 点自动重置
  notify: false    # 重置不发通知,不打扰
```

- 效果:每天凌晨自动归档会话,用户早上第一条消息自动是新会话,无需手动 /new。
- 重置后 agent 收到系统 note("automatically reset... fresh conversation"),照例读日志/晨报恢复上下文,无损。
- 会话内遇到压缩/变长时主动提醒用户:"发 /new 或等明早自动重置"。
- 注意:gateway 从进程内不能重启自己(含 `restart hermes-gateway` 文本的命令被关键词级安全拦截,即便绕过也会 SIGTERM 自杀)→ **用 systemd-run 调度独立脚本延时重启**:脚本文件写 `sleep 3; systemctl restart hermes-gateway`,terminal 命令只含 `systemd-run --on-active=2 --unit=gw-restart-once --no-block /tmp/gw_restart.sh`(不含关键词即可通过);瞬态单元由 systemd 执行,脱离 gateway 进程树,重启时不被连带杀掉;脚本把 `systemctl is-active`+日志写 /tmp 供验证。比 `at` 方案稳(at 需 atd 服务)。重启后积压消息集中涌出属正常。

## 板块设计:有数据才写,无空转(2026-08-13)

- 报告板块按"有数据才写"设计:无数据写"- 无",不编造、不硬凑内容
- 板块类型可含**团队产出类**(如"昨日团队产出:助理/员工各一行"),数据来自产出目录(按天查文件)
- 板块要避免"每天都变但无信息量"的数据源(如自动生成的目录文档),会变噪音
- 换板块时同步更新流程文档中的报告流程图(变更即更新)

## 模式:默认写入 + 可修改重写(用户偏好)

复盘/习惯整理类任务:**默认写入**(Notion/日志区/画像)+ 推送预览 + "要改直接说,我重写更新"。
- 不等待用户确认(用户会忘记回复,日志不能断)
- 用户提修改 → 覆盖重写
- 健康打卡等随手信息:用户随时说 → 立即写入当天日志文件,复盘时以文件为准(不重复提取)

### ⚠️ 重启会打断正在跑的 cron,撞上就报 error 无产出(2026-08-15 实测)

晚间复盘 cron 23:00 启动(23:07:06),正好撞上 gateway 重启(23:07:07)——任务中断,`last_status: error`,无输出文件。gateway 重启(升级/调参/改 MCP 后)会**打断正在执行的 cron agent run**。

对策:
- 重启 gateway 前先查当前时段有没有 cron 在跑:`hermes cron list` 或看 `~/.hermes/cron/jobs.json` 的 schedule;23:00/0:45 等整点附近是复盘/结算高峰,避开
- 撞了怎么办:**补跑**——`cronjob action=run` 手动触发,并注入明确窗口:"这是补跑(原 X 时运行因 gateway 重启中断),数据窗口应为 YYYY-MM-DD HH:MM 至 HH:MM 的完整对话记录"。补跑结果照常投递,`next_run_at` 不受影响(下次定时照跑)
- 完整重启纪律(为什么必须 at 调度等)见 weixin-gateway-ops

## 报告 cron 步骤膨胀治理:预收集脚本注入模式(2026-08-15 周复盘深度重构)

**症状(用户主动发现)**:报告 cron 随着需求增加越改越长——周复盘从 12 步涨到 13 步,每步"读文件/查 API",agent 一趟跑 60-90 次工具调用、10-15 分钟,微信限流风险上升、步骤多质量稀释、token 成本高。用户问"会不会对质量有影响"——会。

**解法(与晚间复盘同款模式的深化)**:**数据收集全部交给预收集脚本(cron `script` 字段),agent 只做判断+写作+输出**:
- 脚本把 agent 需要的数据源一次性提取注入(周复盘 7 类:本周对话/用量/员工成长记录/上周计划/模型观察表/健康打卡/规则迭代;原「决策通道」节 2026-08-15 退役——该异步文件通道已被 frp+SSH 直连替代,监控 cron 一并删除。**过时机制定期清理**:注入脚本里别留已死机制的节,那是噪音)
- prompt 精简到 4 步:①需要判断的查询(如 Notion 待办标记)②生成全文 ③更新记录 ④双版输出
- prompt 写死:"**以注入数据为准,不要再逐个翻文件**;缺失才用 session_search/state.db 补"
- 效果实测:60-90 次工具调用 → ~6 次;时长 10-15 分钟 → 3-5 分钟;注入总量控制在 ~2.7 万字符(≈7k token)

**脚本设计要点(踩坑实录)**:
1. **对话提取必须有总量控制 + 每会话配额**:只设总量上限(如 8 万字符)会被单个超大会话吃光预算,其他会话全丢(实测:9 会话只提取出 2 个,关键内容丢失)。正确:每会话限最近 N 条(`msgs[-20:]`)+ 总量兜底,两者都要。
2. **角色差异化截断 = 不丢精度地瘦身(2026-08-15 实测)**:一味砍总量会丢关键信息。按消息角色给不同配额——user 消息(用户的决策/需求/反馈)保 600 字符基本全保;assistant 消息(过程描述)截 200 字符只留"干了什么"。同样预算下信息密度更高,复盘模型更容易抓重点。实测:总量 2.7万→2.1万字符(省 21%),精度不降反升。口诀:压缩军师的废话,保住老大的原话。
3. **按块过滤"已处理"条目防误报(2026-08-15 实测)**:过滤已处理条目时若按行过滤(剔除含"已处理"的行),已处理条目的**标题仍留在输出**,误报成待处理。正确:按块分割(如 `re.split(r'\n(?=##\s)', text)`),整块含"已处理"标记就整块跳过,只输出真正未处理的块。
4. **dry-run 验证不能只看"能跑"**:跑完统计分节长度(对话/用量/员工各多少字符),确认没有某节异常大/小;输出总长控制在合理范围(≤3 万字符)。
5. **窗口计算要覆盖整周**:周复盘周日凌晨 0:45 跑 → 起点=7 天前 0:00(`back=7; start_date=now.date()-7天`,combine 0:00),覆盖上周日 0:00→周六 24:00;0:10 用量结算已跑完,数据完整。**改任务运行时间必须同步改窗口**(2026-08-15 从 21:00 挪到凌晨时同步改了窗口逻辑)。
6. **Notion 待办等需要判断的动作留给 agent**,脚本不代劳(脚本只提取清单,标记完成要人脑对照对话)。
7. 参考实现:`~/.hermes/scripts/weekly_chat_extract.py`(周复盘)+ `daily_chat_extract.py`(晚间复盘/习惯整理,带 --window-start 参数)。

**⚠️ 步骤膨胀的预防**:报告 cron 每加一个需求,先问"这个数据能不能脚本化提取?"——能就进脚本,不进 prompt。prompt 只保留"需要模型判断"的步骤。

**报告结构排序逻辑(2026-08-15 老大确认)**:生成全文的小节按 5 组组织,并写死进 prompt + 流程文档(标"勿乱改"):
```
📌 回顾   → 本周总览 / 上周计划对照 / ⚠️紧急提示(高优先级遗留前置,紧跟总览,没有则省略)
👥 团队   → 员工表现
📊 运行   → 用量与成本 / 模型观察
📜 制度与身体 → 规则与习惯迭代 / 健康汇总
🎯 行动   → 待办完成 / 遗留问题 / 下周计划 / 一句话小结
```
逻辑:**先对账过去(回顾)→ 再看现状(人/钱/机器/制度/身体)→ 最后定行动**。高优先级风险必须前置(老大先看到问题),不沉底。称呼注意:用户是「老大」不是「老板」(2026-08-15 纠正),所有推送/文档用「老大」。

**复盘类文档统一目录(2026-08-15 老大拍板)**:员工自我复盘与军师复盘集中收 `vault/复盘/`(员工/<岗位·名字>/ + 军师/),与日志体系(vault/日志/每日|周)分家——日志是"时间线记录",复盘是"人的成长",分开互不干扰。周复盘/晚间复盘 prompt 里的复盘读写路径都指向 vault/复盘/。移动文件后必须全局 grep 旧路径(SOUL/守则/prompt/注入脚本/档案全查),零残留。

**复盘质量纳入考核(2026-08-15)**:周复盘注入脚本提取员工复盘文件状态(路径+最近复盘日期),"自我复盘质量"写进员工表现小节(没写直接点名);周复盘自身也含"军师自省"小节(依据 vault/复盘/军师/ 文件)。晚间复盘(23:00)末尾加"军师自省"2-3 条真实自我批评,单独存档 vault/复盘/军师/——军师与员工一样交复盘作业。

**过时机制退役流程(2026-08-15 决策通道退役实战)**:发现某机制被替代/闲置后,完整处置:①停监控 cron ②归档文件(内容合并进历史文档,原文件重置为"停用模板"标注原因——**别直接删文件,留模板防 Obsidian 断链**)③留痕规则演变史/迭代日志(创建→停用时间+原因)④更新引用它的流程文档(如 mermaid 图)⑤清理脚本里的残留节/注释/docstring ⑥grep 验证代码层零残留(注意:输出里残留的"关键字"可能是对话历史等正常内容,需区分代码 vs 文本)。

## 数据注入模式

- 对话提取类(复盘/习惯):用脚本提取当天对话注入 prompt
- 用量/待办类:脚本读取(如 notion_todos.py、token_report.py),0 token
- 避免在 prompt 里写 curl+Authorization 模式(会被安全检测拦截)→ 用独立脚本
- "今天完成/明天计划"汇报的数据源地图(日志模板/cron 输出/会话/定时任务清单)见 references/daily-status-sources.md

## 待办状态同步:任务完结必须主动标记(2026-08-14 老大纠正)

## 定时任务 script 字段坑(2026-08-14 实测)
- **cron 的 `script` 字段只接受纯脚本名,不能带参数!** 写 `daily_chat_extract.py --window-start 20` 会被整个当作文件名,报 "Script not found"
- 需要参数 → 建 wrapper 脚本(`~/.hermes/scripts/xxx.sh`,内部调用 python 并传参),script 字段填 wrapper 纯名
- 排查:`python3 -c "import json; [print(j.get('script')) for j in json.load(open('~/.hermes/cron/jobs.json'))['jobs']]"` 看有没有带空格的
- **脚本语言必须匹配扩展名(2026-08-15 实测)**:cron 按扩展名选解释器——`.sh`/`.bash` 用 bash 跑,其他一切(含无扩展名)用 Python。把 Python 代码写进 `.sh` 文件会被 bash 执行直接语法挂掉(IndexError/语法错)。**Python 内容必须存 `.py`**,然后 cronjob update 里同步改 `script` 指向新文件名(旧名文件要 mv,不能只改内容)。

### ⚠️ Script Error 时 agent 仍继续跑,last_status=ok 会撒谎(2026-08-14)

现象:习惯整理 cron 的 script 配错(带参数),运行时报 `## Script Error: Script not found`,但 **agent 没中断,仍用注入的 prompt 继续执行**(靠记忆/上下文输出),cron 显示 `last_status: ok`。只有打开输出文件才看到 Script Error 段。

对策:
- **验证必须看输出文件内容**,不能只看 last_status:检查 `~/.hermes/cron/output/<job_id>/` 最新 md 是否有 `## Script Error` 段
- 信号提取器(体检类 cron 的数据源)要**只扫 `## Response` 段**,否则会把 Prompt 里注入的报错关键词误报为任务故障(实测晚间复盘 4 连误报);并排除自身 job id
- 改完 script 字段后**手动触发一次**并核对输出,别等下次定时跑才发现

## 周期性「体检/推荐」机制设计模式(2026-08-14 流程推荐实战)

用户会要"定时扫描现有流程/规则/习惯,推荐优化项"。设计模式(与单次报告 cron 不同):

**结构(三层)**:
1. **信号提取脚本**(wrapper 纯名,内部跑 python):扫数据源(cron 输出/executions.db/文档更新时间/技能问题/决策通道)输出结构化信号,0 条写"无"
2. **agent 分析**:按信号规则筛选(高优必须:证据确凿+可执行+改动成本低,缺一不推;存疑标"观察")
3. **只出清单,绝不执行**:用户回"采纳 N"才改;未回答的下轮原样保留,不默认接受/拒绝

**格式铁律**:每条带证据(文件路径/日期/次数),无证据不列;总长 ≤15 行;每周无信号就一句"运行平稳 ✅"不硬凑。

**频率自适应(用户要求,2026-08-14)**:初期数据变化快(如习惯积累期)→ 每周体检;连续 4 周新增/修改 <2 条(进入稳态)→ 自动降为每月。频率跟实际变化节奏走,不是一刀切。

**⚠️ 多份「采纳」报告会串号(2026-08-14 设计时发现)**:周六习惯体检、周六规则体检、周日流程推荐都是"回复采纳 N"——用户隔几天回一句"采纳 1",无法判断是哪份报告的第 1 条。**修复:每份报告带唯一前缀**,回复必须带前缀,如「习惯体检-采纳 2」「规则体检-采纳 1」。

**⚠️ 多份报告分开推送,不要合并成一条消息**:合并发一份消息里两段报告,用户只回其中一个,另一个"没回答"的状态悬空(既非拒绝也非接受),还互相污染编号。规则变化慢→每月、习惯变化快→每周,分开推送正好各按各的频率。

**🚨 新建机制必须"先演示后定稿"(用户纠正,2026-08-14)**:不要建完 cron 直接说"定了"——用户不知道机制实际输出长什么样。流程:建脚本 → **手动触发一次演示运行** → 把真实输出推给用户看 → 用户验收/提意见 → 修 bug → 才正式启用。用户原话:"主要我不知道你现在流程推荐是什么样子的,就直接定下来了吗"。

**去重原则**:多套体检机制(流程推荐/规则体检/习惯体检)共用查重/冲突检测脚本逻辑,不重复造轮子;但 cron 分开、编号独立、频率独立。

**🚨 指纹基线防覆盖(cron 写共享文档时必配,2026-08-14 体检×习惯整理冲突)**:

场景:每晚 20:00 习惯整理(cron)会**追加写**用户画像.md,而周六习惯体检(agent)可能**重构**同一文档(合并/删除/重写条目)。如果体检改完,当晚整理又按旧编号追加 → 体检成果被覆盖。

解法(**条数对比不够,必须 hash 对比**):
- 基线文件存每条条目内容 hash:`~/.hermes/data/habit_baseline.json`(`{"items": {"1":"hash","2":"hash"...}}`)
- cron 的 script wrapper 执行时**先跑基线校验**再跑数据提取:
  - 基线 vs 现状一致 → 正常追加
  - 不一致(合并/删除/新增/**重写**——重写陈述条数不变但 hash 必变)→ 输出硬性锁定指令:"只允许追加新条目(新编号=脚本算好的 max+1);禁止修改/删除/重排旧条目"
- 新编号由**脚本算好注入**,LLM 不数号(杜绝编号错位)
- agent 重构文档后**重新生成基线**(`habit_baseline.py make`),固化新状态
- 参考实现:`~/.hermes/scripts/habit_baseline.py`(make/check 两模式)+ wrapper 里 `check` 输出拼进 prompt

**7 类检查维度(体检"找什么",2026-08-14 用户扩展)**:①重复(两条说一件事→合并)②冲突(多文档说法不一)③过时(30 天未验证)④陈述准确性(含糊/误导/范围不清)⑤陈述优化(更清晰简洁,**只改表述不改边界**)⑥可执行性(指向明确动作,**不写死具体数值/时间/穷举清单**)⑦一致性(同义表达统一)。只查①②③是"修坏东西",漏了④-⑦"让规则越来越好"。

**表述原则(规则/习惯文档写作,2026-08-14 用户多轮纠偏定稿)**:边界完整 + 例子标注"不限于"。
- **边界是权威**:能枚举全就写全(如"重要决策先问:①花钱②账号安全/隐私③不可逆④对外分享/发布⑤已表态事项"),不能穷举的用开放原则描述
- **例子帮助理解,永远标注"例:不限于"**:≤3 个,放边界之后;防被当成完整清单
- 教训:举例时连 agent 自己都会漏(把 5 类说成 3 类),所以边界必须完整,例子只是辅助
- 反例:"注意作息"改成"凌晨0-1点睡"= 写死(作息会变);"边界开放+例子示例"才稳

完整三套机制实现(脚本/基线/输出模板/落地清单)见 references/health-check-mechanism.md。

## 新建 cron 的调度规范(2026-08-14 老大要求)

**① 建任务前先查时间冲突(硬性要求,老大原话"最好就是先看一下会不会有时间冲突")**:定时任务越来越密,新建前必须跑一遍时间表分析,确认目标时段没有同类任务扎堆。参考工具:**`python3 ~/.hermes/scripts/cron_check.py`**(2026-08-15 建,两模式:无参=全量检查现有冲突;带参 `cron_check.py "0 11 * * 6"`=候选时间 ±30min 冲突检查,第三参自定义窗口)。

**② 依赖链任务间隔要留足(实战教训)**:知识库整理(03:30,AI 任务实测 10-20 分钟)→ 目录每日更新(03:40)。10 分钟间隔太近,AI 任务没跑完目录就更新了 → 挪到整理后 1 小时(04:30)。规则:**上游是 AI 任务(时长不定)→ 下游间隔 ≥1 小时**;上游是脚本(秒级)→ 间隔可短。

**②-b 微信发送任务必须间隔 ≥30 分钟(2026-08-18 实战)**:即使有串行锁+冷却补丁,多个 cron 任务密集发送消息到微信仍会撞 iLink 惩罚期(冷却 180s 但退避落在惩罚窗口内)。症状:backing off 180s → 重试 → 再 backoff → 最终 send failed。修复:所有 deliver=weixin 的 cron 任务间隔 ≥30 分钟(如实测:0:00复盘→0:30、7:00夜间检查→7:30)。判断方法:`journalctl -u hermes-gateway --since '...' | grep 'backing off.*180s'` 连续出现=惩罚期未消退,需要更大间隔。**context_from 依赖链也要考虑这个间隔**:上游任务输出发送 + 30min 冷却 → 下游才能安全发送。

**③ 夜间迁移判断启发式**:哪些任务能挪夜间?看结果"是否要用户即时看":
- **无感知型**(整理/备份/结算,结果存文件)→ 适合夜间(00:00-06:00)
- **报告型**(推送报告/总结,用户醒来查看即可,无需当场回复)→ 也适合凌晨(2026-08-15 老大定:周复盘 21:00→周日 0:45、用量提醒每日 0:00→周日 0:30 周总结,理由"白天醒来就能看");凌晨批次依赖顺序:0:10 用量结算 → 0:30 用量周总结 → 0:45 周复盘
- **等确认型**(体检/推荐,推清单等用户"采纳 N")→ 放白天,且**最好周六/周日**(老大周末白天有空)
- 挪夜间时保持依赖顺序(先整理后更新目录),别颠倒

**④ 频率理由写进 prompt 防误改(2026-08-14)**:像"为什么每月一次+为什么放周六白天"这种设计意图,直接写进任务 prompt 开头并标"(勿改)"——否则未来某次排查会被人(含 agent 自己)误当"不合理配置"改掉。频率设计依据:铁律 4(频率匹配信息变化频率)。
